| الحالة | المعنى | عادةً |
|---|---|---|
| `400` | فشل التحقق من الصحة | حقل `settings` مفقود، أو تاريخ ليس بصيغة ISO-8601 |
| `401` | غير مصادَق عليه | ترويسة مفقودة، أو بادئة `Bearer ` لا ينبغي وجودها |
| `403` | غير مسموح | تم بلوغ حد الخطة |
| `404` | غير موجود | معرّف خاطئ — أو معرّف يخص منظمة أخرى |
| `429` | تجاوز حد المعدل | أكثر من 90 طلبًا في الساعة — انتظر ثم أعد المحاولة |

## البنية

```json
{
  "statusCode": 400,
  "message": ["settings.privacy_level should not be empty"],
  "error": "Bad Request"
}
```

تكون `message` سلسلة نصية عند وجود خطأ واحد، ومصفوفة عند فشل عدة حقول.
تعامَل مع الحالتين.

## لماذا يُرجع المعرّف الخاطئ 404 لا 403

الكائن الموجود لكنه يخص منظمة أخرى يُرجع `404`، تمامًا مثل الكائن غير الموجود
أصلًا. وهذا متعمَّد: فواجهة API لا تؤكد أبدًا أن معرّفًا يخص شخصًا آخر حقيقي.

## التحقق من الصحة هو ما ينبغي الاستعداد له

معظم إخفاقات التكامل هي `400` من `POST /posts`، وسببها في الغالب الأعم منصة
تتطلب `settings` لم يرسلها المستدعي. هناك طريقتان لتجنّب اكتشاف ذلك في بيئة
الإنتاج:

1. أنشئ المنشور كمسودة `draft` — إذ يُتخطى التحقق من الصحة — ثم استدعِ
   `GET /posts/{id}/missing` لتُخبَر بما هو ناقص بالضبط.
2. اقرأ [إعدادات القنوات](/ar/public-api/channel-settings) للمنصات التي
   تدعمها.
